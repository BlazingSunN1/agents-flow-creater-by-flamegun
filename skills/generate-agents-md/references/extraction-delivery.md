# 交付链提取清单

仅在任务涉及需求追踪、计划进度、实现、测试、独立验收或模块闭环时读取。

## 需求与最小闭环

- 基线至少固定目标、范围、非目标、约束、可量化验收和版本/哈希；使用稳定 `REQ/FLOW/FEAT/UI/UT/AT/MOD/BB` 编号贯通适用产物。
- AI 主动记录疑问。所有未答项都是 `NON_BLOCKING_P2`，必须带可逆最小影响的 `proposed_default`、`safe_fallback` 和 `assumption` 后继续；人工答复到达时更新基线并只重跑影响范围。
- 稳定交付是流程设计的唯一目的。新增 Agent、产物、门禁、上下文或记录前，绑定已核实风险/失败模式、事实证据、受影响验收、可观测信号和停用条件；无映射就不得新增或启动。
- 先闭合“目标/范围/验收 → 真实入口 → 最小实现 → 可观测结果 → 受影响测试/静态检查 → 当前证据”。冻结同一候选后才做映射的重构、性能、质量或体验打磨；回归时先恢复并重放冻结验收。

## 风险与 Agent

- 小型任务必须影响已知、不改变外部行为/契约/流程且有定向验证。Dispatcher 复用已登记模块维护 Agent（Dispatcher reuses the registered module maintenance Agent）作为唯一写者；不新增独立 Agent、原型、泳道或全链产物。
- 标准任务最多一个写者和一个只读 `BLACK_BOX` 独立验收 Agent，由后者合并变更审查、用例复核和黑盒执行；完整多 Agent 仅用于已证实高风险、并发大模块或明确独立/合规要求。
- Dispatcher 始终只读。主、父、子层级不授予写权；每个实现任务只有一个匹配模块、Agent/run、owned paths 和当前策略哈希的活动写者。独立审查、验收与黑盒 Agent 只读且不得自证或修改代码。
- 跨模块任务逐模块闭环，再由不同的系统聚合写者生成清单；开放缺陷、证据漂移或门禁分歧阻断，不用多数票掩盖。

## 测试、黑盒与文档顺序

1. 实现前定义测试点和适用单元用例；独立验收角色基于已批准基线编写完整成功、拒绝、失败、重试、恢复、权限和边界用例。
2. 实现后运行受影响测试、映射的代码规范检查和自动审查；修复先补失败回归，再做最小根因修改。
3. 独立黑盒 Agent 从类发布入口执行完整验收用例，证据绑定相同基线、代码版本、Build ID、环境、时间和候选哈希。
4. 只有全部适用测试（包括独立黑盒）对同一候选通过后，才写或更新交付/完成文档。计划、需求基线和 `in_progress` 证据可以提前存在，但不得描述未验证工作已交付。

## 计划、进度与日志

- 开发前计划记录目标、范围、顺序、验收、依赖和风险；完成进度记录日期、交付结果、验证证据和剩余事项。
- 日志按稳定模块键和不可变 `run_id` 保存；`run_id` 与 `code_version` 分离。默认只加载生效 `AGENTS.md`、进度索引、当前 run 和相关追踪行；`latest.md` 与历史按需读取。
- 共享记录用 `python3 scripts/flowctl.py record ...` 进行锁、CAS 和原子替换。未运行、未通过、开放缺陷或证据未同步不得标记 `completed`。
- 模块到闭环候选或人工主动触发时才审查；普通代码增量只累计变更与证据。

## 验证入口

- `python3 scripts/flowctl.py plan ...`：从交付契约确定适用门禁。
- `python3 scripts/flowctl.py check trace ...`：验证需求追踪。
- `python3 scripts/flowctl.py check module-close ...`：验证单模块交付包。
- `python3 scripts/flowctl.py check system-close ...`：验证跨模块聚合。
- 验证器缺失、不可运行、失败或证据漂移均失败关闭；未答疑问本身不阻断。
